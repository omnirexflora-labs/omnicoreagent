# 0.5.1: the fixes after 0.5.0

Status: approved (2026-10-06). The maintainer chose 1(a), 2(a) and 3(b).

## Why

0.5.0 shipped with a public list of known issues (`docs/changelog.mdx`, "Known issues"). None of
them breaks a core promise on a normal path. Filming the steward on 0.5.0 (2026-10-05) turned up
three more, from real runs on the test server:

- `run_b6638561`, killed after its push;
- `run_d3826a89`, recorded live.

0.5.1 fixes what was found. It adds no features: the scope is frozen to this list.

## The units

Each unit follows the house rules: a failing test first, then the change, with one unit per commit
and docs changed with the code. A unit marked **verify first** starts with a test that shows the
defect. If that test passes on 0.5.0, the unit is closed with a note instead.

### A. Found while filming (new)

| # | Unit | What we saw | Fix |
|---|---|---|---|
| A1 | **A strict policy silently denies the sandbox's file sync** | Every worker command in both runs was followed by `policy DENY · no rule · sandbox.workspace.sync`. The steward's policy is `mode: strict` with no rule for the runtime's own listing, so no file a worker wrote in the sandbox came back to its workspace. The workers worked around it by writing results through `write_file`. A user writing a strict policy falls into the same trap. | Decision 1. |
| A2 | **Sandbox commands are not in the record under `capture="full"`** (verify first) | `sandbox_exec_started` carries `command_name` and `argc` but not the command text, even though the steward sets `telemetry_config={"capture": "full"}`. `sandbox_exec_completed` has `stdout`/`stderr` but `exit_code` is empty. The live watcher had to read the commands from the model's tool-call arguments. | Under `full`, record the command text (redacted like tool arguments) and the exit code. Under `default`, record name and argc as today, plus the exit code. |
| A3 | **The `tool_calls` budget meter counts more calls than were made** (verify first) | `run_d3826a89`: the meter says 44, while the events show 41 tool calls (lead and workers). `run_b6638561`: 40 against 37. The difference matches the three approved GitHub writes, which suggests a call paused for approval is charged at the pause and again when it runs. | Charge a call once, when it runs. A paused call holds a reservation that is released or kept, never doubled. |

### B. Known issues from the 0.5.0 gate (in the changelog)

| # | Unit | Fix |
|---|---|---|
| B1 | **`read_skill_file` can read a sibling skill's files** (`../other` passes a prefix check) | Resolve the path and require it to sit inside *this* skill's folder (a `Path.is_relative_to` check after `resolve()`), as the workspace tools do. **This is the only security item: it goes first.** |
| B2 | **A worker whose lead crashed stays `running`** | When a lead resumes or is abandoned, settle its workers. A worker whose lead is finished, and whose own lease has lapsed, is marked `abandoned` by the same lease sweep that recovers runs. |
| B3 | **After a crash and resume, the dead segment shows `running`** in trace listings | When a run resumes, close its earlier open segments as `interrupted`, with an end time equal to the last event. The run's record already knows. |
| B4 | **A very small budget pauses on every call** | A budget top-up is granted to the run, not to one call. Check whether the pause is per reservation and fix it so one grant covers the calls it pays for. |
| B5 | **A folder operation under an ask rule is refused, and the message says "does not allow"** | Ask once for the folder operation, naming the covered files. If that is out of scope, at least say "asks" rather than "does not allow", and say why. Decision 2. |
| B6 | **`local` refuses `network_policy: deny` and `image` at the first command** | Refuse them when the agent is built, as every other provider does. |
| B7 | **The generated `.dockerignore` is too broad and too narrow** | Leave out only the workspace path that is actually configured, not every folder named `workspace`. Leave out common credential files (`.env*`, `*.pem`, `*.key`, `.netrc`, `id_*`, `credentials*.json`). |
| B8 | **Two agents sharing one telemetry store share the first one's `retention_days`** | Make retention a property of each write (or refuse two different values on one store, with a clear message). Decision 3. |
| B9 | **The first run in a fresh process starts slowly** (15–60 s client load) | Measure where the time goes (imports, client construction, the network). Fix what is ours; document the rest. No promise of a number. |
| B10 | **Copying many files into a fresh Docker sandbox is slow** (about 0.4 s per file) | Copy as one tar stream, not file by file. |

## Decisions for the maintainer

1. **The sandbox's file sync under a strict policy (A1).** Recommended: **(a)**.
   - **(a)** The sync follows the decision for the command that triggered it. If that command was
     allowed to run in the sandbox, the runtime's own listing afterwards is allowed too. Every file
     it copies back is still decided by the workspace file rules, as today. The listing reads the
     sandbox only, so it adds no reach.
   - **(b)** Keep it a separate capability, but refuse a strict policy that allows sandbox commands
     and not the sync, at build time, with a message naming the rule to add.
   - **(c)** Keep today's behaviour, and only document it.
2. **A folder operation under an ask rule (B5).** Recommended: **(a)**.
   - **(a)** Ask once for the whole operation, listing the covered files.
   - **(b)** Only correct the message, and keep "one by one".
3. **Retention with two agents on one store (B8).** Recommended: **(b)**, since it is the smaller change and has no silent surprise.
   - **(a)** Each record carries its own retention.
   - **(b)** Refuse a second, different `retention_days` on the same store, with a message.

## Findings during the work

- **A3 (confirmed).** The charge ran before authorization, so a call that asked was charged at the
  ask and again when it ran after approval; a denied call was charged twice too. The charge now
  follows authorization. No reservation is held for a paused call: it is not counted until it runs,
  so a pending ask cannot overdraw the budget, and the resume refuses it if the budget has run out.
- **B4 (the plan's premise was wrong).** The pause is not per reservation, and the ledger has
  nothing per call: a grant raises the run's limit. A limit of 1 with a grant of 3 runs four calls.
  The cause is the default amount of a grant, the shortfall of the one call that stopped. The
  default is kept; docs say to name an amount.
